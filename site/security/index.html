Security

Security model

locksql lets an AI agent query a database while a human stays in control.

The console is the enforcement point. Skills, rules and MCP tool descriptions only guide the agent; the console’s checks are the guarantee.

This page summarises the full security model, which is the reference.

Who is trusted

  • Assets: database credentials; the data, personal data in particular; the availability of the database server; the integrity of the data and of the policy that governs access.
  • The human starts the console through lockhub (lox add, lox run), answers it in a terminal (lox attach) and is trusted.
  • The agent, and anything that can steer it (text stored in the database or in files it reads), is not trusted. It runs the client commands and the MCP server.
  • Other local users are not trusted.

locksql runs in Docker: the console and the agent’s MCP server run in Linux containers, on any host that runs Docker (Install).

Principles

  1. Two processes, one key holder. The credentials and the only database connection live in the console. The clients have neither.
  2. The console is the enforcement point. Skills, rules and tool descriptions are guidance. Every check that matters runs in the console.
  3. The AI tightens, the human loosens. Agents may add mask rules or request changes; every loosening needs your confirmation in the console.
  4. Fail closed. What cannot be classified with certainty is refused.
  5. Defence in depth. Server-side read-only and timeouts, a classifier, a full parse and column analysis of reads, a privilege audit, an EXPLAIN gate, result caps, then approval, informed by k-anonymity counts.
  6. Results are data, not instructions.

What the console enforces

One key holder

Credentials are typed at console start (no echo), or read from HashiCorp Vault. They never appear in argv, environment, files, logs, the socket protocol or error messages.

The console disables core dumps. credentials_ttl makes it ask again after a set time (Vault leases).

OS separation

Two containers, built from one image. The console runs as locksql (uid 10001) in one; the agent’s MCP server runs as agent (uid 10002), a member of locksql-clients, in the other.

They share only the socket volume (the socket directory, mode 2710, locksql:locksql-clients). The kernel checks every peer: a process that is neither the console account nor in locksql-clients is refused.

The credentials live only in the console’s container and its lock’s home volume. The console refuses to start without a separated setup, since an agent in its own account could read or type into its terminal. Running locksql in Docker.

Approval outside the agent

Every statement goes to lockhub as a ticket. Only lockhub’s signed decision runs it, and no socket method can approve. The decision is taken in lox run, outside the agent’s harness: by an auto rule the profile allows, or by you.

Writes, schema changes and unmasked reads are asked every time by default; an ask rule makes a ticket never-auto, and the console refuses an auto approval of it. A production ticket is flagged on every facade.

The console’s terminal answers only its own prompts (:review, :unmask). Pending keystrokes are flushed before each, so type-ahead never approves.

Fail closed

A dialect-aware classifier refuses anything it cannot classify with certainty: several statements, comments, variables, bind parameters, file and OS access, sleeps and locks, session tampering.

Reads are limited to SELECT, WITH ... SELECT and EXPLAIN SELECT, parsed in full. Unknown syntax, functions outside an allowlist and system schemas are refused.

Tiers

read < write < ddl < admin; the default is read. Tier read is also enforced server side (read-only session and transaction).

Weight check

A read must carry LIMIT n with n <= max_rows. The console runs EXPLAIN and refuses statements that would examine too many rows, or cost more than explain_cost_refuse. REFUSE cannot be overridden from the console.

PII masking

Every output column is resolved to its source columns, through aliases, functions, subqueries, CTEs, unions, joins and *, and masked on that source, not on its label. Masking is best effort (see the limits below). How masking works.

Statement text

While mask rules exist, pg_stat_statements and pg_stat_activity are refused, since they hold the text of past statements. The MySQL and MariaDB system schemas (performance_schema, sys, information_schema) are outside the console’s catalog and refused.

PII usage

PII columns may be selected, counted, joined with = and filtered with =, IN (literals) or IS NULL. Expressions over them, LIKE, ranges and ORDER BY are refused.

A filter, grouping or aggregate on PII that covers fewer than k_anonymity rows (default 5, production 10) warns you on the ticket; you decide.

No typed values

Placeholders ('${email}') and cell references ('${r1.2.3}') are not supported: no value is typed in lockhub, so a statement holding one is refused at plan time (E_PLACEHOLDER).

Masked cells come back as plain <redacted>. The approval screen warns, in red and in the audit log, when the agent put a clear value in its statement.

Raw values only on your say-so

An agent can ask for unmasked output only when you allowed it in the console: --allow-unmask at start, or :unmask while it runs, confirmed with y, never a single key. Without it the request is refused and audited.

Ctrl-O in the console (or --show-results) shows you the clear rows there while the agent still gets them masked. Both are console-only: no client or config file can turn them on.

Quiet failures

Clients get a generic message, never the server’s error text, and no timings; query.run answers on a 250 ms quantum.

A refusal’s structured form (code, retry rule, hint, place) is written by locksql. The place points into the agent’s own statement and names a keyword, an operator or a name, never a literal, the database’s text or a substituted value.

The AI tightens, the human loosens

Agents may add mask rules and request changes. A config edit that loosens the policy (higher tier, larger limits, new host, removed PII rule, a rule moved toward auto, ...) only takes effect after you confirm it in the console.

Audit

Every login, policy change, refusal (with its code), decision, catalog read, console switch and logout is appended to a JSONL audit log (mode 0600). Each decision names the rule or the human that took it.

Records contain the SQL and metadata, never secrets and never row data.

Untrusted rows

Rows are framed as untrusted data in every output, and the generated agent instructions say so. Control and bidirectional characters are escaped in client output and on the console screen, so data cannot spoof the approval prompt.

What locksql does not protect against

These limits are part of the design. Read them before you rely on locksql.

Same-user mode is excluded

The console refuses to start without a separated setup. An agent running as the console’s account (reading its memory, attaching with ptrace, typing into its terminal) is not a supported configuration.

The console account

Malware running as locksql or as root, and an agent that can become either, are out of scope.

Docker adds one more. Whoever can run docker commands can attach to the console and type an answer, exec into its container and read its memory, or open the lock’s home volume.

An agent that runs shell commands in your account usually can, since the launcher it runs for its MCP server is itself a docker run. That setup keeps the credentials out of the agent’s reach, but it is no boundary against an agent determined to go around it.

For that boundary, run the agent in its own container, without access to the Docker socket (Agent in its own container).

Transport security

Securing the connection to the database is the job of the driver and of the infrastructure (network, SSH tunnel, sidecar, mesh), not of the console. The profile’s tls setting is passed to the driver, with libpq’s sslmode semantics:

The default is prefer, whatever the host. tls_ca is a PEM bundle that replaces the system roots (with require it verifies the chain, as libpq does). tls_server_name replaces host as the name verify-full checks.

tls_cert and tls_key present a client certificate; the key must be mode 0600, in the console account’s files.

locksql checks only that the values are well formed. It refuses no profile because of its tls (production = true included), and no authentication method the driver and the server agree on. A change of a tls* setting does not loosen the approved policy; locksql doctor shows the mode as information.

locksql’s one TLS behaviour is a warning. When the established connection is plaintext, the console says so at session start and records a notice in the audit log; the session proceeds. A TLS connection gets no warning, whatever its verification mode.

Below verify-ca, an active attacker on the path can intercept or downgrade the connection, read and change the traffic, and relay a login. They can obtain the password when the server’s authentication method sends it (MySQL mysql_clear_password or a caching_sha2_password full authentication, PostgreSQL password or md5).

verify-full (with tls_ca for a private CA), or a tunnel to the database’s own host, prevents it.

Through an SSH bastion

A profile with an ssh table reaches its database through a bastion. The console opens the SSH connection in its own process: no ssh binary, no secret in argv, and no local listening port, so another local account (the agent’s included) cannot use the tunnel. The bastion resolves the database’s host name.

The bastion’s host key is checked against the console account’s ~/.ssh/known_hosts. An unknown key is shown with its SHA256 fingerprint and trusted only when you type yes (on a production profile, the fingerprint’s last 8 characters). A changed key is refused with no override.

The key passphrase or SSH password follows the same rules as the database password. The SSH leg is encrypted and the bastion authenticated; the leg from the bastion to the database is protected only by tls, unless the database runs on the bastion.

Adding, removing or changing the ssh table loosens the approved policy. Out of scope: ProxyJump chains, ~/.ssh/config (never read), certificate host keys and forwarding to a Unix socket on the bastion.

Write tiers

Above tier read, the human’s approval is the gate. The classifier assigns the class shown on the screen, but the server does not restrict what an approved write does within the account’s privileges.

While mask rules exist, some writes are parsed and analysed like a read before they run:

  • a write whose rows come back: a RETURNING list on PostgreSQL, MariaDB or SQLite, or a PostgreSQL WITH whose data-modifying CTEs feed an outer SELECT;
  • a write that stores a query’s rows: INSERT/REPLACE ... SELECT, a query in a CTE or in VALUES.

Every returned column is resolved to its base columns. A target column returned by an INSERT or an UPDATE carries both its own provenance and that of the values stored in it. The rows are masked by that provenance, whatever label the engine reports.

Those parts follow the read rules. Anything the parser does not read (MERGE, multi-table MySQL UPDATE/DELETE, PostgreSQL 18 RETURNING old/new, ...) is refused.

So is a PII filter, grouping or aggregate that needs a k-anonymity count, since the count would run the data-modifying CTEs a second time.

The PII filter rules do not apply to the write’s own clauses (its WHERE, FROM/USING items, conflict target). They decide which rows change, which the affected-row count reveals anyway, and the human approves them.

A write that returns no rows and stores no query’s rows is checked by column name only (see copies and planted values).

Size bound

The statement’s size bound counts bytes built from literals and string functions. Numeric arithmetic (1e131071, ^) and formatting of stored data (jsonb_pretty) can still make the server compute and send a value of hundreds of megabytes, bounded by statement_timeout.

The console keeps at most 64 KiB of each cell (cut_cells tells the agent which were cut):

  • PostgreSQL columns are cut while they are read off the wire;
  • MariaDB and MySQL rows are read whole by the driver, up to the server’s max_allowed_packet, and cut before they are copied;
  • SQLite runs in the console’s process, so a value is cut after the driver has copied it out of the database file.

Masking is best effort

Column rules depend on the rules being right, and value detectors catch common formats only. Use a database account that cannot read what the agent must never see.

k-anonymity is a decision aid, not a guarantee

A query whose PII filter, group or aggregate covers fewer than k rows warns you on the ticket; it is not refused, and the warning goes to the audit log. An approved warned query can single out one person. The counts remain a query-set-size control.

Each constant PII filter is counted twice: the subjects of the column in its own base table (a join cannot multiply them; a column of a view, which has no base table to count in, cannot be filtered on), and the rows the statement’s own FROM/WHERE selects.

A join still multiplies the second count. WHERE u.id = 3 AND u.salary IN (...) joined with a large table passes when at least k users earn one of those salaries, and tells the agent that user 3 is among them.

It does not stop differencing attacks: two approved queries whose sets differ by one row (all customers of a city, then the same minus one email) still reveal that row’s other columns. The approval screen shows each PII filter so you can spot such sequences; --unmask queries skip the check.

Equality still leaks equality

A filter WHERE email = 'x@example.com' tells the agent whether that value exists. Under k rows you are warned before approving; once approved, the answer is the agent’s. That is the purpose of this feature.

Equality probing leaves room for a patient agent

An equality filter on a value the agent knows only raises warnings (the clear value, the k-anonymity counts). An agent that spreads such probes across queries or sessions is not stopped: the human reading the tickets is the control.

The unmasked columns of a targeted row still identify it, and free text without a detector is not masked.

Clear results stay on the console’s screen

With the clear results on (Ctrl-O, --show-results) and for an unmasked run, the clear rows stay in the scrollback of the console’s terminal. Anyone who sees that screen sees them (screen sharing, recording, a terminal that logs its output). That terminal is already the trusted party; locksql does not clear it.

Views and inherited tables

A view, a materialized view or a foreign table is masked by column name only: a view that renames a rule column (firstname AS contact) needs its own rule for the new name.

The same holds for a classic-inheritance table (INHERITS) read through a parent or a child the rule does not name. A PostgreSQL partition is resolved to the root of its partition tree, so a rule on the partitioned table covers its partitions.

Copies and planted values at higher tiers

A write (INSERT ... SELECT, UPDATE ... SET, MERGE) that copies a rule column into another column is refused, with or without RETURNING. So is a write that stores into a rule column anything but NULL or DEFAULT.

Columns match by name. An updatable view that renames a rule column, a trigger, or a value written before the rule existed (or by another client) can still put a value the agent knows behind a masked cell.

For the writes analysed like a read, these checks also follow provenance. A value stored from a query that derives from a masked column, through an alias, a table alias column list, a CTE or a derived table, is refused, and a masked target never receives a query’s values.

DDL such as CREATE TABLE ... AS SELECT, CREATE VIEW, a column default or a column rename is not checked that way: at tier ddl and above the human’s approval is the gate.

Catalog metadata

Catalog metadata (database, table, column and index names) is returned without approval.

One console, no sharing

One console per profile and project, one request at a time. No remote or shared consoles, no data export.

How it is tested

  • Fuzzing. The SQL parser and provenance analyzer are fuzzed nightly in CI. Besides panics, the analyzer target checks that an accepted statement never returns a value of a masked column unmasked.
  • Metamorphic tests. Rewrites that keep a statement’s meaning (an alias, a CTE, a subquery, a swapped join, UNION ALL with itself) must keep its provenance in every dialect. A rewrite may be refused, never accepted with a cleaner provenance.
  • PII canary suite. Masked columns are seeded with random canary values on MariaDB 10.11 and 11.4, MySQL 8.0 and 8.4, PostgreSQL 13 and 17 and SQLite. A generated corpus of reads runs through plan, approval, run and masking. The suite fails when an answer to the agent holds a canary, four letters of one, or its hex, base64 or reversed form.
  • No external review yet. The threat model and the analyzer have been reviewed by the maintainer only. An external review is one of the criteria for 1.0; how to contribute one. How the analysis works: docs/pii-analysis.md.

Upstream recommendation

locksql masks what leaves the database; the database still holds plaintext, and any other client of it (a backup, a replica, a reporting tool) sees it.

Where you control the schema, store personal data encrypted at rest with a blind index. The application encrypts the value with a key the database never holds, and stores next to it a keyed HMAC of the normalised value for equality lookups and joins. The database then holds no plaintext to leak.

locksql’s masks are the downstream half of the same idea: they hide values in query results, whatever the database stores. Upstream recommendation in the security model.
