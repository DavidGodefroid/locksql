Install locksql

locksql is built and run as a Docker image: nothing to install but Docker. No Go toolchain is needed; the image’s build stage holds it.

locksql is a pre-release (v0.8.x). The image holds the separated setup: the console runs as the locksql account (uid 10001) in its own container, the only one that holds the database credentials; the agent’s MCP server runs as agent (uid 10002) in a throwaway container. The two share only the socket volume locksql-run, and the kernel checks every peer on the socket.

Other deployment modes (a host install, packages, desktop and session setups) still exist in the code but are no longer documented or supported.

Build the image

Straight from the repository, or with docker build -t locksql . from a clone:

docker build -t locksql https://github.com/DavidGodefroid/locksql.git

For credentials = "vault", build the vault target instead: it adds the vault CLI (some 550 MB), which the default image leaves out.

docker build --target vault -t locksql https://github.com/DavidGodefroid/locksql.git

--build-arg VERSION=v0.8.0 sets the version that locksql version prints. To upgrade, build again and restart the console.

Set up a project

Mount the project at its own path (-v "$PWD:$PWD" -w "$PWD"): the socket name is derived from the project path, so the console and the agent must see the same one. In the project directory, write Claude Code’s files, add a database profile, then give .locksql/ to the console account:

docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD:$PWD" -w "$PWD" locksql init claude
docker run -it --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD:$PWD" -w "$PWD" locksql profile add
docker run --rm --user 0 -v "$PWD:$PWD" -w "$PWD" locksql doctor --fix --yes

--user and HOME make the files yours. init writes .locksql/config.toml with a commented example profile, and .mcp.json with locksql mcp as the MCP command, which is not on your machine: wire the agent replaces that entry.

profile add asks for the engine, host, port, TLS and where the password comes from (typed at console start, or Vault), never for the password itself, and appends the profile to .locksql/config.toml. --engine and its flags skip the questions (locksql profile add --engine postgres --host db.internal --credentials vault --vault-path database/creds/ro). Inside a container localhost is the container itself, and the wizard knows it:

  • a database on your machine is host = "host.docker.internal" (on Linux, add --add-host=host.docker.internal:host-gateway to the console’s docker run). That is not a loopback host, so tls defaults to verify-full: set tls = "disable" or "prefer" for a local server without TLS;
  • a database in another container is reached by its name on a shared network (--network NAME on the console’s docker run);
  • credentials = "keychain" is not available in a container, which has no OS keychain: use ask, or vault with the vault image;
  • a SQLite path is relative to the project root, which is mounted.

The last command runs as root inside the image, where the console account exists. The console writes pii.toml in .locksql/, and a directory your account owns would let the agent replace that file, and with it the masking rules: doctor --fix makes uid 10001 the owner of .locksql/ (mode 0755) and keeps config.toml readable and yours to edit. Its checks of the console and its profiles fail from this container, which runs no console: read the project lines. Run it again whenever .locksql/ is created anew.

Describe your databases

Profiles live in .locksql/config.toml at the project root, the file the console’s container and the agent’s both see. No file ever holds a secret: keys named like password, passwd, pwd, secret or token, and DSNs with an embedded password, are refused.

[profiles.uat]
engine      = "mariadb"             # mariadb | mysql | postgres | sqlite
host        = "db.uat.example.com"  # or path = "app.db" for sqlite
port        = 3306                  # default 3306, or 5432 for postgres
user        = ""                    # empty: asked at console start
database    = ""                    # empty: chosen per query (--db)
credentials = "ask"                 # ask | vault (no keychain in a container)
vault_path  = ""                    # with vault: "database/creds/<role>" or a KV secret
tls         = "verify-full"         # disable | prefer | require | verify-ca | verify-full
tls_ca      = ""                    # optional PEM bundle replacing the system roots
tls_cert    = ""                    # optional client certificate (PEM)
tls_key     = ""                    # its private key (PEM, unencrypted, mode 0600)
tls_server_name = ""                # optional: the name verify-full checks instead of host
credentials_ttl = "20m"             # optional: ask for the secret again
tier        = "read"                # read | write | ddl | admin
production  = false
detectors   = ["email", "phone", "iban", "card", "be_niss"]

[profiles.uat.limits]
statement_timeout   = "30s"
explain_rows_warn   = 100000
explain_rows_refuse = 1000000
max_rows            = 200
max_cell_chars      = 200
max_output_bytes    = 65536
k_anonymity         = 5
explain_cost_refuse = 0             # engine cost units; 0 = off

A remote host defaults to tls = "verify-full": the server certificate must verify, against tls_ca for a private CA; tls_server_name names the certificate’s host when host is an IP address or an alias. tls_cert and tls_key go together, need require or stronger, and present a client certificate when the server asks for one (PostgreSQL clientcert/cert in pg_hba.conf, MySQL REQUIRE X509); keep both files in the console account’s home, the locksql-home volume, the key readable by that account only. On MariaDB and MySQL, a remote host whose certificate is not verified answers no request for the password in clear: connect with verify-ca or verify-full, or use an account with mysql_native_password or ed25519. TLS to the database.

A database reachable only from a bastion gets an ssh table: the console opens the SSH connection itself, with no local listening port, and checks the bastion against the console account’s ~/.ssh/known_hosts, kept in the locksql-home volume, asking on first use and refusing a changed key. host is then the database as seen from the bastion.

[profiles.prod]
engine      = "postgres"
host        = "db.internal"         # as seen from the bastion
tls         = "verify-full"
production  = true

[profiles.prod.ssh]
host        = "bastion.example.com"
user        = "deploy"
auth        = "key"                 # key | agent | password
key         = "~/.ssh/id_ed25519"   # in the locksql-home volume, owned by locksql, mode 0600

Wire the agent

The agent starts the MCP server in a throwaway container, as agent, with the socket volume and the project mounted. sh -c expands $PWD, the directory the agent runs in, so start the agent at the project root. For Claude Code, replace the entry init wrote:

claude mcp remove --scope project locksql
claude mcp add --scope project locksql -- \
  sh -c 'exec docker run -i --rm -v "$PWD:$PWD" -w "$PWD" -v locksql-run:/run/locksql locksql mcp'

--scope user instead wires it for every project. Codex, Gemini CLI and Cursor take the same command (sh) and arguments in their MCP config; keep their tool_timeout_sec or timeout, since the console waits up to 5 minutes for an approval. Agent wiring in the usage guide.

The client commands run the same way, for example docker run --rm -v "$PWD:$PWD" -w "$PWD" -v locksql-run:/run/locksql locksql status.

Start the console

In a terminal you keep in view, from the project directory:

docker run -it --rm --name locksql-console --user locksql \
  -v "$PWD:$PWD" -v locksql-run:/run/locksql -v locksql-home:/home/locksql \
  locksql console --project "$PWD"

Then ask your agent, in the project: “how many orders were placed yesterday?”. Each query waits for your y in the console.

Add --profile P, --show-results, --auto or --allow-unmask after console. The locksql-home volume keeps the console account’s state from one run to the next: the approved policy, the audit log and ~/.ssh/known_hosts for an ssh profile.

With credentials = "vault", add -e VAULT_ADDR=https://vault.example.com to the console’s docker run. The console account needs no vault login: at start the console asks for the Vault token in its terminal (no echo) and keeps it in memory for the session, never on disk. When Vault refuses a read (expired or revoked token, or a policy that may not read the path), it asks again.

Get the token without storing it in your account, where the agent runs, then paste it at the prompt:

vault login -method=oidc -no-store -token-only

A plain vault login would write ~/.vault-token, which the agent could read; do not leave VAULT_TOKEN set in that shell either.

What Docker does and does not separate

The agent’s container holds no credential, has no database connection and reaches the console only through the socket; a process that is neither the console account nor in locksql-clients is refused.

Your own account is another matter. Whoever can run docker commands can attach to the console and type an approval, exec into it and read its memory, or open the locksql-home volume, and an agent that runs shell commands in your account usually can: the MCP server above is itself a docker run. This setup keeps the credentials out of the agent’s reach and the approval in your terminal, but it does not stop an agent determined to go around it. The stronger boundary is to run the agent itself in its own container, without access to the Docker socket, and to build the console’s image with --build-arg ALLOWED_UIDS= set to the agent’s uid.
