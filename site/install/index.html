Install · pre-release v0.17.x

Install locksql

locksql runs in Docker. On your machine you need only Docker and the locksql launcher, a short shell script that runs every command in the locksql image.

With Homebrew

Install with Homebrew
brew trust davidgodefroid/tap
brew install davidgodefroid/tap/lox davidgodefroid/tap/locksql

Homebrew asks you to trust a third-party tap once. brew install davidgodefroid/tap/lockfamily installs the whole family instead.

  1. In your project, lox add locksql asks where your database is. It writes the profile, wires your agent, runs locksql doctor --fix, shows a short review and starts the console.

    lox add locksql

  2. In a terminal of its own, outside any agent, keep lox run open. It serves the decisions: every ticket shows up there.

    lox run

  3. Start your agent in the project and ask it a question about your data.

With lea, run lox add in lea’s projects directory. If lea already runs, lea stop, then lea, brings the new lock in. How lox add works.

Upgrade with brew upgrade locksql, not locksql update.

Without Homebrew

Download the install script from the release you install, read it, then run it with that release:

V=vX.Y.Z
curl -fsSLO "https://raw.githubusercontent.com/DavidGodefroid/locksql/$V/scripts/install.sh"
less install.sh
LOCKSQL_VERSION=$V sh install.sh

It checks the release’s cosign signature and checksum, and installs the launcher as /usr/local/bin/locksql. The launcher runs the image of its own release, ghcr.io/davidgodefroid/locksql:X.Y.Z, which Docker pulls on first use.

Linux and macOS (Docker Desktop); on Windows, install it in WSL 2 with Docker Desktop.

  • locksql version prints the launcher’s version and its image’s.
  • locksql update installs the latest release’s launcher and pulls its image.
  • LOCKSQL_VAULT=1 selects the image with the vault CLI (some 550 MB more) for the launcher’s commands; the console’s image is the lock’s, which lox add pins.
  • LOCKSQL_IMAGE runs an image of your own, such as docker build -t locksql . from a clone.

What runs where

The console runs as the locksql account (uid 10001) in its own container. It is the only one that holds the database credentials.

The agent’s MCP server runs as agent (uid 10002) in a throwaway container. The two share only the console’s socket volume, and the kernel checks every peer on the socket.

Set up a project by hand

lox add runs these for you. By hand, in the project directory: write the agent’s files, add a database profile, then check the setup and repair what can be.

locksql init claude      # or codex, cursor, gemini
locksql profile add
locksql doctor --fix --yes

init and profile run as you, so the files are yours. init writes .locksql/config.toml with a commented example profile, the agent’s instructions, and an MCP entry locksql mcp: the launcher (wire the agent).

profile add asks for the engine, host, port, TLS and where the password comes from: typed at console start, or Vault. It never asks for the password itself.

--engine and its flags skip their questions; --non-interactive asks none (locksql profile add --non-interactive --engine postgres --host db.internal --credentials vault --vault-path database/creds/ro).

Inside a container localhost is the container itself, and the wizard knows it:

  • a database on your machine is host = "host.docker.internal", which the lock’s egress gateway maps to your machine. tls defaults to prefer: a local server without TLS connects in plain TCP, with a warning;
  • a database in another container: publish its port on your machine and name host.docker.internal; under lox run the lock reaches only its profile’s endpoints and cannot join the container’s network (lockhub#194);
  • credentials = "keychain" is not available in a container, which has no OS keychain: use ask, or vault with the vault image;
  • a SQLite path is relative to the project root, which is mounted.

doctor --fix runs as you. It wires your agents and keeps .locksql/ as lox run reads it: copied once for the console, which never reads the project, taking only files and directories that are yours and that no one else can write.

Entries the console account owns (uid 10001, left by doctor --fix up to v0.13.0) are given back to you as root, in a container of its own run only then. Its checks of the console warn from this container, which runs no console.

Describe your databases

Profiles live in .locksql/config.toml at the project root, the file both the console’s container and the agent’s see.

No file ever holds a secret. Keys named like password, passwd, pwd, secret or token, and DSNs with an embedded password, are refused.

[profiles.uat]
engine      = "mariadb"             # mariadb | mysql | postgres | sqlite
host        = "db.uat.example.com"  # or path = "app.db" for sqlite
port        = 3306                  # default 3306, or 5432 for postgres
user        = ""                    # empty: asked at console start
database    = ""                    # empty: chosen per query (--db)
credentials = "ask"                 # ask | vault (no keychain in a container)
vault_path  = ""                    # with vault: "database/creds/<role>" or a KV secret
tls         = "verify-full"         # disable | prefer (default) | require | verify-ca | verify-full
tls_ca      = ""                    # optional PEM bundle replacing the system roots
tls_cert    = ""                    # optional client certificate (PEM)
tls_key     = ""                    # its private key (PEM, unencrypted, mode 0600)
tls_server_name = ""                # optional: the name verify-full checks instead of host
credentials_ttl = "20m"             # optional: ask for the secret again
tier        = "read"                # read | write | ddl | admin
production  = false
detectors   = ["email", "phone", "iban", "card", "be_niss"]

[profiles.uat.limits]
statement_timeout   = "30s"
explain_rows_warn   = 100000
explain_rows_refuse = 1000000
max_rows            = 200
max_cell_chars      = 200
max_output_bytes    = 65536
k_anonymity         = 5
explain_cost_refuse = 0             # engine cost units; 0 = off

The tls settings go to the driver as they are, and the default is prefer whatever the host. Set tls = "verify-full" to verify the server certificate, with tls_ca for a private CA.

tls_server_name names the certificate’s host when host is an IP address or an alias. tls_cert and tls_key go together and present a client certificate when the server asks for one; keep both in the console account’s home, the lock’s home volume that lox run creates.

TLS to the database

A database reachable only from a bastion gets an ssh table. The console opens the SSH connection itself, with no local listening port. It checks the bastion against the console account’s ~/.ssh/known_hosts, asking on first use and refusing a changed key.

host is then the database as seen from the bastion.

[profiles.prod]
engine      = "postgres"
host        = "db.internal"         # as seen from the bastion
tls         = "verify-full"
production  = true

[profiles.prod.ssh]
host        = "bastion.example.com"
user        = "deploy"
auth        = "key"                 # key | agent | password
key         = "~/.ssh/id_ed25519"   # in the lock’s home volume, owned by locksql, mode 0600

Wire the agent

locksql works with any MCP client. locksql init claude|codex|cursor|gemini writes the project files, the instructions and the MCP command locksql mcp.

That command is the launcher: it starts the MCP server in a throwaway container, as agent, with the socket volume and the project mounted. Start the agent at the project root, or below it.

For every project instead of one, add the same command to the agent’s user config. Claude Code, for example:

claude mcp add --scope user locksql -- locksql mcp

Codex, Gemini CLI and Cursor take the same command (locksql, argument mcp) in their MCP config. Keep their tool_timeout_sec or timeout long, since the console waits up to 5 minutes for an approval.

Agent wiring in the usage guide

Start the console

The console runs attached to lockhub only. lox add locksql declares the lock; lox run, in a terminal of its own outside the agent, starts the hub and the workspace’s locks, then serves the decisions.

lox attach NAME attaches your terminal to the console (detach: Ctrl-P Ctrl-Q). There it asks its policy, the PII rules and the password; it asks again when it restarts.

lox run starts the console, never the launcher: locksql console exits with the console is started by lox run only (lockhub): run lox run in the workspace. It runs as the locksql account in its own container, one per lock.

The lock’s home volume, <compose project>_<instance>-home, keeps the console account’s state from one run to the next: the approved policy, the audit log, and ~/.ssh/known_hosts for an ssh profile.

With HashiCorp Vault

With credentials = "vault", declare the lock with Vault: lox add locksql NAME --credentials vault --vault-path PATH --vault-address URL pins the vault image and writes the vault: block of lockfamily.yaml, from which lox run gives the console VAULT_ADDR. The console account needs no vault login.

At start the console asks for the Vault token (no echo), on a card in lox run’s terminal, and keeps it in memory for the session, never on disk. When Vault refuses a read, it asks again.

Get the token without storing it in your account, where the agent runs, then paste it at the prompt:

vault login -method=oidc -no-store -token-only

A plain vault login would write ~/.vault-token, which the agent could read. Do not leave VAULT_TOKEN set in that shell either.

Running locksql in Docker, the full guide

What Docker does and does not separate

The agent’s container holds no credential, has no database connection and reaches the console only through the socket. A process that is neither the console account nor in locksql-clients is refused.

Your own account is another matter. Whoever can run docker commands can attach to the console and type an answer, exec into it and read its memory, or open the lock’s home volume.

An agent that runs shell commands in your account usually can: the launcher it runs for the MCP server is itself a docker run. This setup keeps the credentials out of the agent’s reach, but it does not stop an agent determined to go around it.

The stronger boundary: run the agent itself in its own container, without the Docker socket, and start the console with --allowed-uids set to the agent’s uid (or build its image with --build-arg ALLOWED_UIDS= and run it with LOCKSQL_IMAGE). Agent in its own container.
