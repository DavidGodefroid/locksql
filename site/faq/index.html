FAQ

Frequently asked questions

Short answers, each drawn from the README and the docs. For anything not covered here, see the usage guide.

Which databases does locksql support?

MariaDB 10.1+, MySQL 8.0+, PostgreSQL 13+ and SQLite 3. All engines are pure Go. See supported engines.

Which AI agents does it work with?

Any MCP client: Claude Code, Codex, Cursor, Gemini CLI, … each starts the MCP server with the same command, locksql mcp (wire the agent).

An agent can also use the locksql CLI from a shell.

Which operating systems? Does it run on Windows?

Anything that runs Docker: Linux, macOS, and Windows through WSL 2 with Docker Desktop, on amd64 and arm64. The console and the agent’s MCP server run in Linux containers; locksql does not run natively on Windows. Install.

How do I set it up?

Install lox and locksql with Homebrew. In your project, lox add locksql asks where your database is (never the password), sets up the lock and starts its console.

Keep lox run open in a terminal of its own: it serves the decisions. Then start your agent. The install guide, also by hand.

Does the agent ever see my database password?

No. The agent never sees a credential and never opens a connection. Credentials are typed at console start (no echo), or read from HashiCorp Vault.

They never appear in argv, environment, files, logs, the socket protocol or error messages. No config file may hold a secret.

Can the agent approve its own queries, or turn approval off?

No. A statement runs only on lockhub’s signed decision: no socket method approves, and no socket method loosens the policy.

Decisions are taken in lox run, outside the agent. Its auto mode approves only what the profile’s rules allow (reads, by default); writes, schema changes and unmasked reads are asked every time. The rules live in a file the agent sees read-only, and loosening them is a reviewed change.

Why does the console need its own OS account?

An agent in the console’s own account could read or type into its terminal. Separation is mandatory: without it the console refuses to start.

The image sets it up: the console runs as locksql (uid 10001) in its own container, the agent’s MCP server as agent (uid 10002) in another. They share only the socket volume, and the kernel checks every peer.

Whoever can run docker commands can still attach to the console: what Docker does and does not separate.

What happens if I don’t answer?

Nothing runs. The agent gets pending with a ticket, and the statement runs only once the ticket is approved in lox run. If lox run is not open, tickets wait at the hub (fail closed). A denial reaches the agent with your reason.

Can locksql run writes or DDL?

Tiers are read < write < ddl < admin; the default is read, which is also enforced server side. Above tier read your approval is the gate: the server does not restrict what an approved write does within the account’s privileges.

While mask rules exist, a write that returns rows (RETURNING, data-modifying CTEs) or stores a query’s rows (INSERT ... SELECT) is analysed like a read, and its rows are masked by where they come from. Write tiers.

How is personal data protected?

Every output column is traced to its source columns and masked on that source, not on its label; value detectors mask the other cells. Modes are redact (the default), partial and email.

Quasi-identifiers (birth date, postal code, gender) are never masked unless you accept them one by one. Masking is best effort: use a database account that cannot read what the agent must never see. More on masking.

Can the agent look up a customer by email without seeing it?

Not by a typed value. Placeholders ('${email}') and cell references ('${r1.2.3}') are not supported, since no value is typed in lockhub: a statement holding one is refused at plan time (E_PLACEHOLDER).

Masked cells come back as plain <redacted>. More.

Can I see the real values myself?

Yes: press Ctrl-O in the console (or start it with --show-results). It prints each result in clear, in the console only; the agent still gets the masked cells.

If the agent itself must see raw values, start the console with --allow-unmask, or type :unmask in it. Only then may it ask for an unmasked query, which you still approve one by one. More on these switches.

Does k-anonymity stop all inference?

No. It is a decision aid: a query whose PII filter, group or aggregate covers fewer than k rows warns you on the ticket, and you decide. It does not stop differencing attacks that combine several approved queries. See the example.

Is the connection to the database encrypted?

As your profile says. The tls setting goes to the driver with libpq’s sslmode semantics (disable, prefer, require, verify-ca, verify-full); the default is prefer.

Set tls = "verify-full" to verify the server certificate, tls_ca for a private CA, tls_server_name when the certificate does not name host, and tls_cert/tls_key for a client certificate.

locksql enforces none of it and only warns when the connection is plaintext. For a server behind a bastion, add an ssh table: the console opens the tunnel itself, checks the host key and listens on no local port. Full details.

Why was my query refused, and what should the agent do?

Every refusal carries a stable code (E_NO_LIMIT, E_COST, E_MASKED_FILTER, …), the place where the check stopped, a hint and a retry rule: rewrite (once), ask_user (only you can lift it) or stop.

MCP clients get it as structured content. locksql stats counts your refusals by code; --export anonymises them for an issue. More on refusals · all codes.

Can text stored in the database manipulate my agent?

It can. locksql assumes the agent may be steered by data, so it treats the agent, and anything that can steer it, as not trusted. Every check runs in the console.

Rows are framed as untrusted data in every output, and control and bidirectional characters are escaped so data cannot spoof the approval prompt.

Can the agent change the policy?

Agents may add mask rules and request changes. A change that loosens the policy only takes effect after you confirm it in the console. How policy changes work.

What is logged?

Every login, policy change, refusal, decision, run, catalog read, console switch and logout, in a JSONL audit log (mode 0600). The approval is written before the statement runs, its outcome after. Records hold the SQL and metadata, never secrets and never row data.

Can several people share one console, or export data?

No: one console per profile and project, one request at a time, no remote or shared consoles, no data export.

Do I need Go to install it?

No. locksql runs from its release image, which Docker pulls; Homebrew and the install script only put the launcher on your machine. Building from a clone needs Go 1.26 or Docker. Without Homebrew.

Is locksql stable?

It is a pre-release (v0.17.x): any release may still change the config files, the MCP tools or the CLI. The path to 1.0 lists what must be true first, among others an external review and frozen contracts.

The SQL analyzer is fuzzed nightly and a canary suite checks for leaks on real engines: how it is tested.

What is the Lock Family?

A set of Locks for AI agents, one per kind of data source (databases, queues, files, HTTP, logs, SSH), all answered by one hub, lox run. lockfamily.dev.

How do I report a vulnerability?

Privately, through GitHub security advisories, not in a public issue. See SECURITY.md.
