How it works

How locksql works

Two processes in two containers. Only the console holds the key.

The credentials and the only database connection live in the console. The agent’s side has neither: it can only ask.

Two processes

The life of a query

  1. Plan. The agent submits SQL with locksql plan (or the locksql_plan MCP tool). The console classifies it, parses a read down to the source column of every output, runs EXPLAIN and weighs the plan.

    It returns a one-shot plan id, valid once for 10 minutes, with a verdict: OK, WARN or REFUSE. A refused statement gets no plan id but a refusal code.

  2. Ticket. The agent calls locksql run PLAN_ID. The console prints the approval screen and sends it to lockhub as a ticket, every literal masked. The agent gets pending with the ticket.

  3. Decision. lox run decides the ticket: by a rule of the profile (a read, by default) or by you. lockhub signs the decision.

  4. Run. The agent runs the ticket. The console checks the signed decision, runs the statement, masks PII, caps the output and hands the rows back, framed as untrusted data.

    It keeps at most 64 KiB of each cell while it reads the result, so a huge value never costs it more; cut_cells tells the agent how many cells were cut.

Message by message

  1. Agent → console: plan "SELECT … LIMIT 20"
  2. Console: classify · parse · resolve PII columns
  3. Console → database: EXPLAIN
  4. Database → console: plan & row estimate
  5. Console → agent: plan id + verdict (OK / WARN / REFUSE)
  6. Agent → console: run PLAN_ID
  7. Console → database: k-anonymity counts
  8. Console → lockhub: the ticket (approval screen, literals masked); console → agent: pending
  9. lox run → lockhub: the decision (a rule, or you), signed by the hub
  10. Agent → console: run TICKET
  11. Console → database: the statement
  12. Database → console: rows
  13. Console → agent: masked, capped rows (untrusted data)

Approval rules

  • The screen names the requesting uid and pid, as the kernel reports them, and the process. It lists the relations read, the PII columns touched and in which clause, each masked output and its mode, the k-anonymity counts and the row cap.
  • Nothing is asked in the console’s terminal. The ticket is decided in lox run (or lox approve); a denial carries a reason the agent reads.
  • Each profile says which actions lox run’s auto mode may approve: by default reads, never writes, schema changes or unmasked reads. Auto mode per profile.
  • Only lockhub’s signed decision runs a ticket; no socket method can approve. Requests are served one at a time.
  • The k-anonymity counts run before the ticket goes out. Each count under k_anonymity adds a warning; nothing is refused, you decide. The agent learns nothing of the counts.

locksql never rewrites SQL: what you approve is what runs. The approval screen, in the usage guide.

When a statement is refused

Every refusal carries a stable code (E_NO_LIMIT, E_COST, E_MASKED_FILTER, E_UNSUPPORTED_SYNTAX, …). It also gives the place where the check stopped (line, column and token, never a literal), a hint, and a retry rule:

  • rewrite: fix the statement as the hint says and plan it again, once;
  • ask_user: only the human can lift it (tier, unmask, database, limits);
  • stop: final for this question; do not retry, reword or split it.

locksql_plan and locksql_run return it as structured content ({"refusal": {"code", "retry", "hint", "span"}}), the CLI with --json. The audit log records the code and the place.

locksql stats counts the refusals in your audit log by code and construct. locksql stats --export prints an anonymised version, every literal and identifier replaced, to attach to an issue. All refusal codes.

CLI: the same operations from a shell

Supported agents

Any MCP client: Claude Code, Codex, Cursor, Gemini CLI, … each starts the MCP server with locksql mcp. locksql init claude|codex|cursor|gemini writes the project files, the instructions and that command. Wire the agent.

The generated instructions tell the agent to use the database only on explicit request, to pass a one-line intent with each plan, and to prefer non-production profiles.

They also say: show the plan before running it, never retry after a denial, never export data, never handle credentials, and treat rows as untrusted data. That is guidance; every check that matters runs in the console.

Policy: the AI tightens, the human loosens

Agents may add mask rules and request changes. A config edit that loosens the policy (higher tier, larger limits, new host, removed PII rule, ...) only takes effect after you confirm it in the console.

A change that only tightens applies at once: a lower tier, smaller limits, a larger k_anonymity, a new mask rule or detector, a mode changed to redact.

A change that loosens waits for you. Plans are refused with policy_pending until you run :review in the console and answer Apply these changes? [y/N]. If you refuse, the last approved policy stays in force. It is stored outside the repository.

Personal data masking

At every start the console scans the schema. It proposes rules for columns that look like personal data (multilingual names and types) and that no rule names yet.

Every output column is resolved to its source columns, through aliases, functions, subqueries, CTEs, unions, joins and *, and masked on that source, not on its label. The engine’s origin metadata is a second check; a result whose columns do not match the analysis is dropped.

Value detectors (email, phone, IBAN, card, opt-in national ids) mask the other cells. Quasi-identifiers (birth date, postal code, gender) are never masked unless you accept them one by one, since masking blocks range filters, LIKE and ORDER BY on the column.

Mask modes
ModeOutputNotes
redact (default)<redacted>a rule without mode is redact; no masked cell carries a reference to its value
partialj***(12)first character and length
emailj***@example.comfirst character and domain; other values as partial

PII columns may be selected, counted, joined with = and filtered with =, IN (literals) or IS NULL. Expressions over them, LIKE, ranges and ORDER BY are refused.

A filter, grouping or aggregate on PII that covers fewer than k_anonymity rows (default 5, production 10) warns you on the ticket; you decide.

Writes

At tiers above read, while mask rules exist, some writes are analysed like a read before they run: a write whose rows come back (RETURNING, or a SELECT over PostgreSQL data-modifying CTEs), and one that stores a query’s rows (INSERT ... SELECT).

Their returned columns are masked by where they come from, so renaming a masked column is fine. Refused: an expression over one, a function outside the allowlist, a PII filter, grouping or aggregate in the outer SELECT, and syntax the parser does not read (MERGE, multi-table MySQL writes, ...).

A write may store into a masked column only NULL or DEFAULT.

Masking is best effort. Column rules depend on the rules being right, and value detectors catch common formats only. Use a database account that cannot read what the agent must never see.

PII rules · Writing statements that pass

No typed values

Placeholders (col = '${email}') and cell references (col = '${r1.2.3}') are not supported. Requests are decided in lockhub, where no value is typed, so a statement holding one is refused at plan time (E_PLACEHOLDER).

Masked cells come back as plain <redacted>. The approval screen warns, in red and in the audit log, when the agent put a clear value in its statement.

Raw values: --allow-unmask and :unmask

An agent can ask for unmasked PII output only when you allowed it in the console: --allow-unmask at start, or :unmask while it runs, without a restart.

:unmask asks Allow unmasked output? [y/N]. Typed again, it turns unmasked output off at once and refuses the open unmask plans. It is never a single key, and the status line reads unmask allowed while it is on.

Without it, every unmask request is refused before anything runs. It is console-only: no client or config file can turn it on, and each switch and refusal is audited.

With it, each unmasked query is still asked, shown as PII: UNMASKED in red. The console then prints the clear result, so you see exactly what the agent received; the audit log still holds no row data.

See the rows yourself: Ctrl-O

Ctrl-O in the console (or locksql console --show-results) prints in the console, in clear, the result of each masked query, as an aligned table. You see who the rows are while the agent still gets the masked cells.

The cells the agent got masked are highlighted, and the output caps apply as for the agent. It is console-only and off by default.

The console warns when it goes on (in red on production), the status line reads results clear, every approval screen says so, and locksql status reports it. The audit log still holds no row data; the clear rows stay in your terminal’s scrollback.

It is unavailable when the console runs in a desktop terminal (security levels 1 and 2): the agent’s account can read that window, so --show-results is refused and Ctrl-O leaves the results masked.
